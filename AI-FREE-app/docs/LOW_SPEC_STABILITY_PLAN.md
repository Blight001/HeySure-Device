# AI-FREE 低配置电脑稳定性落地方案

> 状态：待实施  
> 适用范围：Windows x64 桌面端、Electron 外壳、AI-FREE Chromium Fork 运行时  
> 目标问题：低配置电脑上软件闪退、浏览器栏目打不开、启动超时、隐藏栏目持续占用资源  
> 编写日期：2026-08-14

## 1. 背景与当前判断

AI-FREE 使用 Electron 作为控制面，并为每个浏览器环境启动独立的 AI-FREE Chromium Profile。当前已经具备 Chromium 完整性预检、沙箱 ACL 检查、握手超时、进程树清理、会话恢复、运行耗时日志和独立崩溃看门狗，但资源保护仍不完整。

当前主要风险如下：

1. 新建 Chromium 前不检查可用内存、提交内存、磁盘余量或当前进程数量。
2. 普通用户的五窗口限制是产品权限限制，不是设备容量限制；VIP 用户没有基于设备能力的并发上限。
3. 浏览器设置中的“内存”代表指纹暴露值，不是 Chromium 的实际内存配额。
4. Electron 和 Chromium 默认关闭后台节流，并长期启用 `prevent-app-suspension`，隐藏环境仍可能持续消耗 CPU、内存和电量。
5. Chromium 默认需要在 30 秒内完成 Runtime Bridge 握手，低速 CPU、机械硬盘、杀毒扫描或严重换页可能造成假性超时。
6. Chromium 崩溃后当前会关闭对应栏目，没有受控重试和可操作的错误页；主程序看门狗负责收集、上传异常，不负责防重启循环的恢复启动。

因此，本方案不以“隐藏错误”或“无限重试”为目标，而是在启动前阻止必然失败的操作、运行中降低资源压力、失败后提供有限恢复，并留下可度量的验收证据。

## 2. 目标与非目标

### 2.1 目标

- 资源不足时不再盲目启动新的 Chromium 进程。
- 低配置电脑默认只运行设备实际承受得住的浏览器环境数量。
- Chromium 冷启动较慢时减少误判，真正失败时在明确时限内退出。
- GPU 兼容性故障允许一次受控的无 GPU 重试。
- 浏览器异常退出后保留可见、可操作的错误状态，不表现为栏目突然消失。
- Electron 主进程异常退出后可恢复，但必须阻止崩溃重启循环。
- 所有资源决策和失败原因均可通过脱敏日志定位。

### 2.2 非目标

- 不承诺在任意低配置、资源耗尽或已损坏的 Windows 系统上强行运行。
- 不使用 `--single-process`、`--no-sandbox` 等降低安全性的 Chromium 参数换取资源下降。
- 不静默回退到系统 Chrome、Edge 或 Electron `webContents` 承载业务网页。
- 不把浏览器指纹中的 CPU/内存字段当作资源调度依据。
- 不在出现资源压力时直接强杀用户正在操作或正在执行自动化任务的环境。

## 3. 实施前置条件

当前工作树正在修改 Chromium 预检、启动、关闭、性能日志和标签生命周期。实施本方案前必须先完成以下动作：

1. 将当前 Chromium 启停重构作为一个独立基线完成评审、测试和提交。
2. 确认新拆出的 `chromium-runtime-launch.js`、`chromium-handshake-waiter.js`、`chromium-preflight-warmup.js` 等文件是后续工作的真实入口。
3. 不在两个分支中同时修改 `chromium-runtime.js`、`browser-tab-launcher.js` 和 `tab-manager-runtime.js`。
4. 保持生产文件不超过 500 行、函数不超过 80 行、圈复杂度不超过 15；资源策略、平台采集和 UI adapter 分文件实现。

## 4. 总体设计

```text
Windows / Electron 资源采集
          │
          ▼
SystemResourceMonitor ── 周期快照、压力等级、迟滞
          │
          ├──► BrowserCapacityPolicy ── 计算设备并发上限
          │
          ├──► BrowserLaunchGuard ── 启动前 allow / warn / deny
          │
          └──► BackgroundWorkPolicy ── 隐藏环境和自动化任务策略
                                      │
用户新建栏目 ──► LaunchGuard ──► 预检 ──► spawn ──► handshake ──► attach
                      │                                      │
                      └─ 拒绝并显示原因       失败 ──► 有限重试/错误栏目
```

建议新增模块：

| 模块 | 建议位置 | 职责 |
| --- | --- | --- |
| `system-resource-monitor.js` | `src/app/main/platform/` | 采集内存、磁盘、CPU、系统信息并发布不可变快照 |
| `browser-capacity-policy.js` | `src/app/main/features/browser/` | 纯函数，根据快照、活动任务和配置计算容量 |
| `browser-launch-guard.js` | `src/app/main/features/browser/` | 在创建占位栏目和 Chromium 进程前作准入判断 |
| `chromium-launch-recovery.js` | `src/app/main/browser-runtime/` | 识别可重试故障、生成唯一一次重试动作 |
| `crash-loop-guard.js` | `src/app/main/runtime/` | 记录异常退出频率，决定正常恢复或安全模式 |

模块返回稳定结果，不直接拼接 UI 文案：

```js
{
  ok: false,
  code: 'BROWSER_RESOURCE_MEMORY_CRITICAL',
  retryable: true,
  snapshot: {
    pressure: 'critical',
    availableMemoryMb: 612,
    freeDiskMb: 7420,
    activeProfiles: 2,
    profileLimit: 2
  }
}
```

日志和 IPC 中不得包含 Profile 路径、账号、Cookie、Token、代理凭据或网页正文。

## 5. 第一阶段：资源准入和并发保护

### 5.1 资源快照

启动完成后创建单例 `SystemResourceMonitor`，默认每 5 秒刷新一次，启动浏览器前强制获取一次不超过 2 秒的新快照。

首版至少采集：

- 物理内存总量、可用内存。
- Electron 主进程工作集。
- 已运行 AI-FREE Chromium Profile 数量及其 PID。
- Profile 根目录所在磁盘的剩余空间。
- CPU 逻辑核心数。
- 是否开启低配模式、是否处于电池供电状态（可后续加入策略，首版只记录）。

采集失败不得直接导致应用退出。快照必须带 `status: available | partial | unavailable`，关键值未知时采用保守容量，不伪造为零。

### 5.2 首版保守阈值

以下数值是首版默认值，必须通过第 10 节的真实机器测试校准，不应写死在多个业务文件中：

| 条件 | 动作 |
| --- | --- |
| 可用内存 `< 768 MB` | 禁止新建 Chromium |
| 可用内存 `768 MB–1.5 GB` | 警告；仅允许当前无 Chromium 时启动一个 |
| Chromium/Profile 磁盘剩余 `< 2 GB` | 禁止新建，并提示清理磁盘 |
| 总内存 `<= 4 GB` | 设备容量上限 1 个 Profile |
| 总内存 `> 4 GB 且 <= 8 GB` | 设备容量上限 2 个 Profile |
| 总内存 `> 8 GB 且 <= 16 GB` | 设备容量上限 3 个 Profile |
| 总内存 `> 16 GB` | 默认容量上限 5 个 Profile |

最终允许数量取以下最小值：

```text
产品权限上限、设备容量上限、管理员配置上限、全局安全硬上限
```

VIP 只能提高产品权限上限，不能绕过设备容量上限和全局安全硬上限。建议全局安全硬上限首版设为 8，待压力测试后再评估。

### 5.3 压力等级与迟滞

资源压力使用 `normal / warning / critical` 三态。必须使用迟滞，避免可用内存在阈值附近波动导致 UI 和策略反复切换：

- 进入 `critical` 后，可用内存连续 15 秒高于恢复阈值才回到 `warning`。
- 进入 `warning` 后，可用内存连续 30 秒稳定才回到 `normal`。
- 已运行环境不因一次采样进入 `critical` 而被直接结束。

进入严重压力后的动作顺序：

1. 停止新的 Chromium 预热和非必要后台初始化。
2. 拒绝新建浏览器环境。
3. 提示用户关闭隐藏环境或其他大型软件。
4. 仅在用户确认后关闭非活动环境。
5. 正在执行自动化任务的 Profile 必须标记为受保护，不自动关闭。

### 5.4 接入点

- 在 `BrowserTabLauncher.launchNewTab()` 创建占位标签之前执行准入，避免失败后 UI 闪一下再消失。
- AI 工具创建浏览器、浏览器历史恢复、手动新建必须共用同一个 `BrowserLaunchGuard`，不能各自复制判断。
- `FREE_BROWSER_WINDOW_LIMIT` 保留为产品权限常量，不再被当作设备安全上限。

## 6. 第二阶段：低配模式和后台资源策略

### 6.1 低配模式启用方式

提供三种状态：

- `auto`：默认，根据总内存、核心数和真实运行压力选择。
- `on`：用户强制启用保守策略。
- `off`：用户关闭低配优化，但仍不能绕过 critical 资源门禁和安全硬上限。

自动模式首版可在总内存不超过 8 GB 或逻辑核心不超过 4 时启用。该判断只决定优化策略，不直接代表系统不可运行。

### 6.2 后台节流调整

当前全局关闭后台节流的做法应改为按任务需要保护：

1. 主窗口和普通侧栏恢复 Electron 默认后台节流，侧栏不应永久设置 `backgroundThrottling: false`。
2. `powerSaveBlocker` 只在存在活动自动化任务、下载或必须维持实时连接时启动；最后一个租约释放后停止。
3. Chromium 的 `--disable-backgrounding-occluded-windows` 在低配模式下默认不传。
4. 自动化任务开始时申请 `BackgroundExecutionLease`，结束、超时、取消、崩溃和应用退出时都必须释放。

首版不要尝试在运行中的 Chromium 上动态切换所有命令行特性。需要改变进程级参数时，在 UI 中明确提示“重启该浏览器环境后生效”。

### 6.3 指纹“内存”字段改名

UI 中的“内存”改为“设备内存指纹”，并补充说明：

> 仅影响网页可见的设备信息，不限制浏览器实际内存占用。

实际资源策略显示为独立的只读信息，例如“本机建议同时运行 2 个环境”，不要将两者混为一个配置项。

## 7. 第三阶段：启动超时和有限恢复

### 7.1 分阶段超时

保留现有性能 span，将启动拆成可观测阶段：

- 资源准入。
- Profile 准备。
- 后台预检等待。
- 沙箱与完整性预检。
- 进程启动。
- Runtime Bridge 握手。
- HWND 附着。
- 启动后配置。

建议策略：

- 正常模式握手默认 30 秒。
- 自动识别的低配模式或首次冷启动默认 60 秒。
- 不允许无上限延长；总启动预算建议不超过 90 秒。
- 用户主动取消或关闭栏目时必须立即取消等待，不能等满超时。

阈值后续根据 P95 冷启动数据调整，而不是依据单台开发机体验修改。

### 7.2 错误分类

| 分类 | 示例 | 是否自动重试 |
| --- | --- | --- |
| 资源不足 | 内存 critical、磁盘不足 | 否，等待资源恢复 |
| 安全/完整性失败 | 哈希失败、非 NTFS、沙箱 ACL 失败 | 否，不降低安全策略 |
| 可执行文件缺失 | runtime 不完整 | 否，提示修复安装 |
| GPU 初始化/进程崩溃 | 明确 GPU 相关诊断 | 最多一次无 GPU 重试 |
| 握手超时 | 进程仍存活但未 hello | 低配冷启动最多一次延长重试 |
| HWND 附着失败 | 握手成功但嵌入失败 | 清理后最多一次重建宿主窗口 |
| 用户取消 | 关闭创建中的栏目 | 否 |

### 7.3 重试约束

- 同一次用户操作最多自动重试一次。
- 重试前必须确认旧进程树已经退出、Profile 锁已释放、Host HWND 已销毁。
- GPU 安全重试只在诊断明确指向 GPU 初始化或 GPU process crash 时加入 `--disable-gpu`。
- 不允许使用 `--no-sandbox`、系统浏览器回退或忽略完整性失败。
- 两次失败后必须停止，并展示稳定错误码、简短说明、重试按钮和诊断目录入口。

## 8. 第四阶段：崩溃后的用户恢复

### 8.1 Chromium 栏目

Chromium 异常退出时不要立即删除栏目。将栏目转成 `crashed` 错误状态，并保留：

- 原栏目名称和 Profile ID 的内部关联。
- “重新打开”按钮。
- 符合条件时的“使用兼容模式重试”按钮。
- “打开诊断目录”按钮。
- “关闭栏目”按钮。

错误页不得显示完整本地路径、命令行、代理凭据或网页内容。重新打开应复用已有稳定 Session 恢复逻辑。

### 8.2 Electron 主程序

在现有 crash watchdog 之外增加 `CrashLoopGuard`：

- 最近 10 分钟只有一次异常退出：允许自动恢复一次。
- 最近 10 分钟异常退出达到 3 次：禁止自动重启，进入安全模式提示。
- 安全模式默认不自动恢复 Chromium 栏目、不启动 Clash、不执行后台预热，并建议关闭硬件加速。
- 用户正常退出、安装更新退出不得计入崩溃循环。

自动恢复功能必须在打包态真实验证。开发态不应自动拉起多个 Electron 实例。

## 9. UI 与错误信息

浏览器创建入口统一展示：

- 当前运行环境数，例如 `2 / 2`。
- 当前资源状态：正常、资源紧张、资源不足。
- 被拒绝时的直接原因和建议动作。

建议稳定错误码：

| 错误码 | 含义 |
| --- | --- |
| `BROWSER_RESOURCE_MEMORY_CRITICAL` | 可用内存不足 |
| `BROWSER_RESOURCE_DISK_CRITICAL` | Profile 磁盘空间不足 |
| `BROWSER_DEVICE_CAPACITY_REACHED` | 达到设备容量上限 |
| `CHROMIUM_GPU_START_FAILED` | GPU 初始化失败 |
| `CHROMIUM_SAFE_RETRY_FAILED` | 兼容模式重试仍失败 |
| `APP_CRASH_LOOP_DETECTED` | 主程序进入崩溃循环保护 |

提示语应告诉用户“发生了什么、能做什么”，不要只显示“启动失败”。

## 10. 测试方案

### 10.1 单元测试

必须覆盖：

- 各内存档位的容量计算。
- 产品权限、设备容量、管理员上限和安全硬上限取最小值。
- 快照缺失、部分字段不可用、采集异常。
- warning/critical 迟滞和恢复。
- 活动自动化租约的申请、释放、超时与重复释放。
- GPU、完整性、握手、附着和用户取消的重试分类。
- 同一次启动最多重试一次。
- CrashLoopGuard 的正常退出、单次崩溃和连续崩溃。

### 10.2 集成测试

- 所有浏览器创建入口共用准入策略。
- 拒绝启动时不创建占位栏目、不创建 Profile 锁、不启动子进程。
- 创建中进入 critical 不破坏已经成功 spawn 的状态机。
- Chromium 异常退出后保留错误栏目。
- 兼容模式重试前旧进程和 HWND 已完全释放。
- 应用退出时所有后台租约、monitor、timer 和 Worker 均释放。

### 10.3 故障注入

需要可重复注入：

- Chromium spawn 返回 `ENOMEM`。
- 握手永不到达。
- Chromium 在握手前退出。
- GPU process `oom/crashed`。
- HWND 附着连续失败。
- 磁盘不足。
- 资源采集 API 超时或抛错。
- Chromium 已退出但进程树清理超时。
- Electron 连续三次非正常退出。

### 10.4 真实设备矩阵

至少准备以下环境：

| 设备 | 磁盘/GPU | 场景 |
| --- | --- | --- |
| 4 GB、2–4 核 | HDD、老旧核显 | 1 个环境冷启动、页面加载、关闭重开 |
| 8 GB、4 核 | SATA SSD、核显 | 1/2/3 个环境并发、隐藏后台、AI 自动化 |
| 16 GB、4–8 核 | SSD、核显/独显 | 1/3/5 个环境、长期运行 |
| 32 GB 以上 | NVMe | 5/8 个环境压力上限验证 |

每个档位都测试：

- 首次冷启动和第二次热启动各 10 轮。
- 连续打开/关闭 50 轮。
- 浏览器运行 2 小时。
- 内存压力下打开新环境。
- 硬件加速开启/关闭。
- Clash 开启/关闭。
- 杀毒实时保护开启状态下冷启动。

## 11. 指标与验收标准

每次启动记录脱敏结构化指标：

- `resourcePressure`
- `availableMemoryMbBucket`
- `activeProfiles`
- `profileLimit`
- `launchMode`：normal / low-spec / gpu-safe
- 各启动阶段耗时
- 最终结果和稳定错误码
- 是否发生自动重试

不得记录原始 Profile 路径、网页 URL、Cookie、账号或代理凭据。

首版完成定义：

1. 4 GB 测试机资源不足时能稳定拒绝第二个环境，不发生 Electron OOM 闪退。
2. 8 GB 测试机同时运行两个典型网页环境 2 小时，Electron 主进程不异常退出。
3. 所有资源不足拒绝都在创建 Chromium 子进程前发生。
4. Chromium 崩溃后栏目保留错误状态，用户可以手动重试或关闭。
5. GPU 故障自动重试最多一次，不形成重启循环。
6. 冷启动 P95 小于对应模式的握手预算，超时后无残留 Chromium 进程、Profile 锁或 Host HWND。
7. 连续打开/关闭 50 轮后，Chromium 进程数回到零，日志、监听器、Worker 和 timer 无持续增长。
8. `npm run verify` 全部通过，新增策略关键分支覆盖率不低于 90%。

## 12. 分阶段交付顺序

### Milestone A：观测与资源门禁

- 新增资源快照、容量策略和启动准入。
- UI 显示设备容量与拒绝原因。
- 增加资源策略单元测试和启动入口集成测试。
- 不改变 Chromium 后台策略和崩溃 UI。

### Milestone B：低配模式

- 增加 `auto/on/off` 配置。
- 将 power blocker 改为租约式生命周期。
- 低配模式恢复非必要后台节流。
- 改正“设备内存指纹”UI 文案。

### Milestone C：有限启动恢复

- 引入错误分类和单次重试控制器。
- 低配冷启动使用扩展握手预算。
- GPU 明确故障时执行一次无 GPU 重试。
- 验证失败清理和会话恢复。

## 13. 发布与回滚

- 每个 Milestone 独立提交、独立开关、独立验收，不把所有策略一次性发布。
- 资源门禁首版可以先以 `observe-only` 记录 1 个版本，再启用拒绝；但磁盘严重不足可以直接硬拒绝。
- 低配策略和自动恢复都必须有远端或本地 kill switch。
- 回滚只能关闭新策略，不能回滚 Profile 数据格式或删除用户会话。
- 若出现误拒绝，优先调整集中策略配置，不在多个入口增加临时绕过。
